# tool の出力から JSON の字下げを除く

## 目的

LLM が tool の出力に払うトークンを、中身を変えずに減らす。

TASK0006 の計測（[記録](../records/20260926_tool-output-size.md)）で、FastMCP が tool の
戻り値を 2 桁字下げの JSON にしていると分かった。整えた後の 3 つの出力を字下げと区切りの
空白を除いた JSON にすると、36〜40% 縮む（`dict` を返す 2 つは実際の出力とほぼ同じ量で
測った）。字下げは全ての tool に付いている。

## 目標

- 全ての tool の出力を、字下げと区切りの空白を除いた JSON にする
- `list` を返す tool の出力を、要素ごとのブロックでなく JSON の配列 1 つのテキスト
  ブロックにする（裁定 2026-09-26。概要設計「`list` を返す tool」）
- 出力の中身（キーと値）は変えない
- 後から足す tool も、個別に書かずに同じ形で出る
- 変更の前後の出力の大きさを実測し、記録へ残す（記録層）

## 非目標

- 出力の中身を絞ること（TASK0006 が扱った）
- Mod（C#）の変更
- resource の出力（すでにブリッジの本文をそのまま返している）

## 問題

- **FastMCP の変換は戻り値の型で分かれる。** `dict` は 1 つのテキストブロック、`list` は
  要素ごとのブロック、`str` はそのまま渡る（`mcp` 1.27.1 の `func_metadata.py` の
  `_convert_to_content`）。文字列にして返すと、`list` を返す tool のブロックの分け方も
  変わる
- **戻り値の型注釈が合併型だと、structured content として同じ結果をもう一度送る。**
  TASK0006 の `get_animals` がこれに当たり、`structured_output=False` で塞いだ。全 tool を
  文字列にする形なら、出力スキーマの扱いも同時に決まる
- 86 の tool に一律に効かせるので、個別に書き換えるより、FastMCP の変換の手前で 1 箇所に
  寄せる形が要る。upstream へ送れる形にするかは計画時に決める
- `list` を返す tool の実際の出力に対する割合は測っていない（TASK0006 の記録の注記）
- **要素ごとのブロックは、一覧の形を受け手へ伝えない**（2026-09-26 実測。`mcp` 1.27.1 の
  サーバーをメモリ上で起動して確かめた）。空の一覧は 0 ブロックで返り、受け手には何も
  届かない。1 要素の一覧は `dict` を返す tool と同じ 1 ブロックになる。要素が文字列なら
  引用符の無い素のテキストになる。テストの `call()` も「1 要素の一覧はその要素として
  読む」と注記して、この曖昧さを抱えている
- 86 の tool の戻り値の注釈は `dict` 65・`list` 20・`dict | list` 1 である。素の
  `dict`・`list` からは FastMCP が出力スキーマを作らないので、structured content を送る
  のは合併型の 1 つだけである（`_try_create_model_and_schema` を読んだ）

## 概要設計

### 効かせる場所

FastMCP の `tool()` デコレーターは、どれも `add_tool()` を通って登録される。`FastMCP` を
継承したサーバーの型を 1 つ置き、`add_tool()` だけを上書きする。

- 上書きした `add_tool()` は、登録する関数を「戻り値を字下げの無い JSON 文字列にする」
  ラッパーでラップしてから、元の `add_tool()` へ渡す。ラッパーは `functools.wraps` で元の
  関数の名前・説明・引数・注釈を引き継ぐので、tool の名前・説明・入力スキーマ・
  `Context` の注入は変わらない
- ラッパーはサーバーの型の private な静的メソッドに置く。関数の注釈（`-> dict`）と
  クライアントが受け取る形（JSON のテキスト）が食い違うことを、structured output の
  拒否と同じ場所で読めるようにするため
- 86 の `@mcp.tool()` は書き換えない。サーバーを作る 1 行を新しい型へ替えるだけで、後から
  足す tool も同じ経路を通る。`add_tool()` を通らない登録（コンストラクターの
  `tools=[...]`、tool manager への直接の登録）はラップされないので、登録済みの全 tool が
  ラッパーを通ることをテストで見る
- デコレーターは元の関数を返す（ラップした関数は登録にだけ使う）。テストや他の関数から
  直接呼ぶ `collect_overview` 等は、今までどおり Python の値を返す
- 見送った案: 86 の tool を個別に書き換える（差分が大きく、新しい tool が漏れる）。
  `mcp` の内部関数 `_convert_to_content` の差し替え（非公開の関数に依存し、版の更新で
  黙って外れる）

### 直列化

- 標準ライブラリの `json.dumps(result, ensure_ascii=False, separators=(",", ":"))` で書く
- `ensure_ascii=False` は必須である。既定のままだと日本語の 1 字が `\uXXXX` の 6 字に
  なり、出力がかえって膨らむ
- FastMCP の直列化（`pydantic_core.to_json(..., fallback=str)`）とは、JSON にできない値を
  文字列にする逃げ道の有無が違う。tool の戻り値はブリッジの本文を `r.json()` で読んだ値
  と、それを整えた値だけなので、JSON にできない値は現れない。現れたら黙って文字列に
  せず、型を名指す失敗として出す方を採る
- ラッパーが受ける戻り値は、JSON が持てる値（dict・list・文字列・数・真偽・None）に
  限る。pydantic のモデル・`Image`・content block 等の FastMCP 独自の扱いは使えなくなる。
  この制約はラッパーの docstring に書き、失敗することをテストで固定する
- NaN と Infinity は JSON にない表記のまま書く。FastMCP の既定（`inf_nan_mode` が
  `constants`）も同じ表記だったので、前後で変わらない
- 浮動小数の表記は両者で違いうる（`1e-05` と `1e-5` 等）。値は変わらないので、中身の比較は
  JSON として読んだ値で行う
- 戻り値が `str` でも JSON の文字列として書く。一覧の中の文字列と同じく引用符が付き、
  全ての出力が JSON になる。該当する tool は今は無い

入力と出力の例（テストの期待値の元になる）:

| tool の戻り値 | 変更前のブロック | 変更後のブロック |
|---|---|---|
| `{"a": 1, "b": "ラベル"}` | 1 つ: `{\n  "a": 1,\n  "b": "ラベル"\n}` | 1 つ: `{"a":1,"b":"ラベル"}` |
| `[]` | 0 個 | 1 つ: `[]` |
| `[{"a": 1}]` | 1 つ: `{\n  "a": 1\n}` | 1 つ: `[{"a":1}]` |
| `[{"a": 1}, "x"]` | 2 つ: `{\n  "a": 1\n}` と `x` | 1 つ: `[{"a":1},"x"]` |

### 出力スキーマ

- ラッパーは文字列を返すので、出力スキーマを持つ tool では FastMCP の検証と食い違う。
  上書きした `add_tool()` は `structured_output=False` を固定して渡す
- 呼び出し側が `structured_output=True` を明示したら、黙って上書きせず `ValueError` で
  拒む。それ以外の引数は位置でも名前でも、そのまま元の `add_tool()` へ渡す
- これで `get_animals` の個別の `structured_output=False` とその注記は要らなくなるので外す

### `list` を返す tool

一覧全体を JSON の配列 1 つのテキストブロックにする（裁定 2026-09-26）。

- 空の一覧が `[]` として届く。1 要素の一覧と `dict` を見分けられる。文字列の要素に引用符が
  付く（「問題」の実測）
- 受け手は LLM で、ブロックの境界に意味を読ませる仕組みはこのサーバーに無い。ブロックの
  境界ごとにクライアントが足す費用も消える
- 保つ案（要素ごとのブロックのまま、各要素の字下げだけを除く）は既存の振る舞いを最も
  変えないが、上の 3 つの曖昧さが残る

### テスト

- `mcp_server/tests/test_tools.py` の `call()` は、1 つのブロックを JSON として読む形へ
  直す（「1 要素の一覧はその要素として読む」の読み替えが要らなくなる）
- 出力の形は、ブロックの本文が「JSON として読んで字下げ無しで書き直した文字列」と一致する
  ことで確かめる。字下げが 1 か所でも残れば一致しない
- 全 tool の出力スキーマの有無は `list_tools` で見る。呼ばずに全 86 件を覆える
- 後から登録した tool は、テストの中で新しい tool をサーバーへ足して呼ぶ
- 登録済みの全 tool の関数がラッパーであること、ラップしても説明と入力スキーマが
  ラップしない登録と等しいこと、JSON にできない値・NaN・`structured_output=True` の扱いを
  それぞれテストで見る

### 計測

- 計測器 `tools/measure_tool_output.py` を足す（fork ローカル）。変更前と変更後の
  `main.py` をそれぞれ読み込み、メモリ上のサーバーから必須の引数を持たない `get_*` の
  tool を全て呼ぶ（52 件のうち該当するもの）。GET 以外の要求は計測器が拒む
- 1 回目（変更前）はブリッジの本文を tool ごとに記録し、2 回目（変更後）は記録した本文を
  同じ tool へ返す。ゲームの時間が進んでも、前後は同じ本文に対する出力になる。通信の
  失敗も記録し、2 回目で同じ失敗を起こす
- tool ごとに文字数・バイト数・ブロック数と、前後を JSON として読んだ値の一致を出す。
  値は型まで比べる（`1`・`1.0`・`true` を区別する）
- 各側の出力は、その側の tool 関数が返した値の型で読む（FastMCP は `list` を要素ごとの
  ブロックで書く）。もう片方の出力の形からは決めないので、前後とも字下げの無い形でも
  測れる（TASK0010 での再利用）
- 2 つの `main.py` は、それぞれ隣のモジュール（`shaping` 等）を自分のフォルダから読む。
  ただし 1 つのインタープリターで走るので、入っているライブラリは共有する
- 終了コードは、前後が同じなら 0、どれかの tool が違えば 1、計測器を信頼できなければ 2。
  `--json` は tool ごとの大きさと判定、2 つの `main.py` の SHA-256 と `mcp` の版を書く。
  出力の本文は残さない
- あわせて `list_tools` の結果（名前・説明・入力スキーマ・annotations）を前後で照合する。
  ゲームを要さないので、実機の計測の前に回せる
- TASK0006 の計測スクリプトは追跡しておらず、測り直せなかった。TASK0010 でも同じ計測が
  要るので、今回は追跡下に置く

### upstream へ送れる形

- 実装は作業書と別のブランチで行い、fork ローカルのファイルに触れない（TASK0006 と同じ）
- 送るかどうかは本作業で決めない（残課題）
- 送るなら追加の作業が要る。`get_animals` の変更箇所は fork 固有で、upstream の
  `-> list` と衝突する。upstream にはテストが無く、`test_tools.py` を持ち込めない。
  upstream の利用者にも出力の形の変更になるので、upstream 側での告知が別に要る。
  `mcp` の版の上限（`<2`）も upstream の `pyproject.toml` を変える

## 検証

実機では中盤のセーブで、読み出しの tool 36 件の出力を同じブリッジの本文に対して前後で

該当しない（推論。スタブの較正は反映後の実装で通る）。
