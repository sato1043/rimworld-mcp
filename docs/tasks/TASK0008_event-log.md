# 前回から起きた出来事を差分で引けるようにする

## 目的

LLM が「前回見てから何が起きたか」を、取りこぼしも重複もなく知れるようにする。

今の `/messages` は letter を最新 30 件返すだけで、通し番号も時刻も持たない。LLM は
前回と今回の応答を突き合わせるしかなく、新しい出来事を見分けられない。`/incidents` も
同じ形である。TASK0005 の残課題で、利用者がこの改善を挙げた。

## 目標

- 出来事（letter とメッセージ）を、前回の続きから引ける読み出しを足す。応答は出来事の
  一覧と、次に渡す続きの位置（カーソル）を持つ
- 各出来事は、発生した tick・種類（letter かメッセージか）・ラベル・letter の種別を持つ
- 取りこぼしがありうる場合（古い出来事が捨てられた・セーブを読み直して tick が戻った）を、
  応答で明示する
- 読み出しを呼ぶ MCP の tool を足す
- 続きの位置で出来事を選ぶ規則を、ゲームの型に依存しない純粋関数へ切り出し、自動テストを
  成果物として残す

提供要求（SREQ）は採番しない。このリポジトリは要求一覧を持たない（TASK0003 の裁定）。

## 非目標

- 既存の `/messages`・`/incidents` と、それを呼ぶ tool の変更。TASK0006 の複合 tool が
  `/messages` を読むので、形を保つ
- TASK0006 の複合 tool を、この読み出しへ切り替えること（両方の統合後に検討する）
- サーバーから LLM へ出来事を push すること（WebSocket 等）
- 出来事の本文（letter の説明文）。量が大きいので、ラベルと種別に留める

## 問題

事実は RimWorld 1.6 の `Assembly-CSharp.dll` のリフレクションと、IL の呼び出し先から
確かめた（作業記録を参照）。

- **出来事はゲームの記録（`Find.Archive`）から拾う。** letter とメッセージはどちらも
  `IArchivable` で、受け取った時点で記録へ入り、セーブに残る。記録への出入りは
  `Archive.Add` と `Archive.Remove` を通る（間引きも `Remove` を呼ぶ）
- **位置を tick だけで表すと取りこぼす。** 一時停止中は tick が進まず、読んだ後にも同じ
  tick の出来事が増える（エージェント自身のコマンドが出すメッセージを含む）
- **位置を番号だけで表しても取りこぼす。** letter は作った時点で番号を取り、受け取った
  時点の tick を持つ。遅延して届いた letter は、先に読んだ letter より小さい番号を持ちうる
- **同じ tick の中の並びは当てにならない。** 記録は追加のたびに tick で並べ直されるが、
  その並べ替え（`List.Sort`）は安定でない。同じ tick の出来事ばかりのとき、追加した
  ばかりの出来事が先頭に並んで、そのまま間引かれうる。記録の中身を外から見比べる方法では
  これを見られない
- **メッセージの番号は、記録へ入った順を表さない。** 番号は作った時点で振られ、記録へ
  入るのは送った時点である
- **記録は古いものから捨てられる。** ピン留めしていないものが letter とメッセージを
  合わせて 200 件を超えると消える。ただし間引けないもの（`CanCullArchivedNow` が偽。
  画面に残る letter 等）は飛ばすので、古い順に消えるとは限らない。位置より後の出来事が
  消えていれば、応答でそれを示す
- **セーブの読み直しは tick では見分けられない。** 位置より後の時点のセーブを読めば
  tick は戻らない。番号の採番もセーブとともに巻き戻る
- Mod の読み出しそのもの（`GameStateReader`）は自動テストで確かめられない。選ぶ規則を
  純粋関数へ切り出し、そちらをテストする（TASK0003 の `RequestGuard` と同じ形）

## 概要設計

### 読み出しと tool

- 読み出し: `GET /events?since=<位置>&limit=<件数>`。`since` を省くと、記録にある最新の
  `limit` 件を返す。`limit` は 1〜200、既定 30。不正な `since`・`limit` は 400
- 応答: `{"events": [...], "next": <位置>, "more": <bool>, "gap": <bool>,
  "reloaded": <bool>}`。`events` は記録へ入った順に並べる。各出来事は `tick`・`kind`
  （`letter` / `message`）・`type`（def 名）・`label` を持つ。ラベルを読めない出来事は
  `label` を null で返し、ゲームのログへ 1 回警告する（1 件のために読み出し全体を
  止めない）
- 大きさ: 中盤のセーブで `limit=200` の応答は 23,675 バイト（letter 37・メッセージ 163、
  最長のラベル 59 文字）だった。TASK0006 が半減させた `get_animals`（約 22 KB）と同じ
  規模である。`limit` の上限 200 は、記録が間引かずに持つ件数（ピン留めしていないもの
  200 件）に合わせた。1 回で記録の全体を引ける
- tool: `get_events(since: str = "", limit: int = 30)`。説明文で「前回の応答の
  `next` をそのまま次の `since` に渡す」と LLM に伝え、`gap`・`reloaded` の意味を書く。
  省いた引数は TASK0006 の tool に揃えて空の文字列で表し、空の `since` は送らない
  （読み出しが 400 で拒むため）。読むだけの tool なので `readOnlyHint` を付ける

### 位置（カーソル）

LLM が中身を解釈せずに渡し返す文字列にする。中身は `世代.通し番号` の 2 つ。

- **通し番号**: 記録へ入った順に Mod が振る番号。Harmony で `Archive.Add` の前に
  割り込んで振る。他の Mod の prefix より先に振り（`Priority.First`）、他の Mod が
  `Add` を置き換えて自分で記録へ入れる場合にも番号が付くようにする。`Add` が出来事を
  入れなかったとき（他の Mod の取り消し・例外）は、最後に走る finalizer が、その呼び出しで
  振った番号だけを返す。読み手の誰も見ていない番号なので、消えた扱いにしない。セーブから
  読み込んだ出来事は `Add` を通らないので、読み込みの直後（`FinalizeInit`）に台帳を空に
  して、tick・種類・番号の順で振り直す（読み込み中に `Add` を通った出来事も並べ直す）。
  読み出しの直前には台帳を記録と照合し、番号の無い出来事に同じ順で振り、番号を持つのに
  記録に無い出来事を消えたものとして扱う（割り込みが外れたときの受け皿）。照合が何かを
  拾ったら、割り込みが出入りを取りこぼしている証拠なので、台帳を「不確か」にする
- **世代**: 番号を振り直すたびに作り直す乱数。`FinalizeInit` で振り直しと同じ場所で
  作る。台帳と世代は `MCPGameComponent` が持つ（ゲームごとに作られる）。位置の世代が
  今と違えば `reloaded` を立て、`since` なしと同じく最新を返す

世代が同じでも、このロードで振っていない番号（振った最大の番号より大きい）の位置は
受け入れない。`since` なしと同じく最新を返し、`gap` を立てる。

選ぶ条件は「通し番号が位置より大きい」だけである。件数の上限で切れたら、返した最後の
番号を次の位置にし、`more` を立てる。切れていなければ、それまでに振った最大の番号を次の
位置にする（間に間引かれた出来事を、`gap` で知らせたうえで越える）。`since` なし・
読み直し・振っていない位置では、最新の `limit` 件を返し、振った最大の番号を次の位置に
する。それより前は読んだものとして扱い、`more` を立てない。

`gap` は、Harmony で `Archive.Remove` の後に割り込んで、消えた出来事の通し番号の最大を
覚えて決める。「消えた最大の番号が位置より大きい」ときに立てる。追加と同時の間引きも
`Remove` を通るので捉えられる。割り込みの中で失敗した場合は、ゲームの処理を止めずに
台帳を「不確か」にし、ゲームのログへ警告を書く（ロード・手順・例外の型ごとに 1 回）。
照合や割り込みが取りこぼしを見つけて「不確か」にした場合も、ロードごとに 1 回警告する。
ただし読み込み中は、セーブから読んだ出来事に番号が無いのが正常なので警告しない。
不確かな間は、このロードの位置を渡した応答で `gap` を常に立てる（取りこぼしを否定できない
ため）。位置なしと読み直しの応答は最新から返し直すので立てない。次に読み込むと台帳を
振り直すので「確か」へ戻る。Harmony の patch が当たらなかった場合も、読み込みのたびに
台帳を「不確か」にし、Mod の起動時に 1 回警告する。patch に失敗してもブリッジは起動する。

### 選ぶ規則（純粋関数）

入力は出来事ごとの通し番号・位置・件数の上限・今の世代・振った最大の番号・消えた最大の
番号・台帳が確かか。出力は選んだ出来事の添字・次の位置・`more`・`gap`・`reloaded`。通し
番号の台帳・1 回の読み出しの手順（照合・番号を引く・選ぶ）・位置の文字列への変換と解析・
問い合わせの解釈も同じ側に置く。`RequestGuard` と同じく、ゲームの型を参照しないファイルに
置く。リポジトリの慣行どおり 1 ファイル 1 型で `MCP/Source/MCP/Events/` へ分け、テストの
プロジェクトはこのフォルダを `Compile Include` で取り込む。本番の読み出しとテストは同じ
読み出しの手順を呼ぶ。ゲーム側は、出来事の型の判定と読み出しを `ArchiveEvents` の 1 か所に
置く。

    1. 構造を先に変える（振る舞いは変えない）: 純粋ロジックを 1 ファイル 1 型で
       フォルダへ分け、テストのクラスも型ごとに割る。読み出しの手順を純粋側へ移し、

    4. 実機で、遊んでも照合の警告が出ないこと、劣化させた 2 本のビルドで `gap` と警告が

#### 実機

共通の前提と復元を先に置く。各シナリオの欄はこれを指す。

- 共通の前提: ゲームの `Mods` にある Mod のジャンクションを実装の worktree の `MCP/` へ

  ビルドを使ったシナリオでは、実装のブランチの作業ツリーを戻してビルドし直す

- **続きから引く**

- **振っていない位置**
