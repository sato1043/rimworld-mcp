# 全ての tool に読み書きの性質を示す annotations を付ける

## 目的

MCP クライアントと LLM が、tool を呼ぶ前にそれがゲームを変えるかどうかを知れるようにする。

TASK0006 の CP6（攻撃者視点）で、ゲーム内の文字列（手紙のラベル・名前等）が状況把握の
出力に集まり、同じ文脈で書き込みの tool を呼べると指摘された。どの tool にも MCP の
annotations が無く、クライアントは読み出しと書き込みを区別して承認できない。TASK0006
では複合 tool にだけ `readOnlyHint` を付けた。

## 目標

- 全ての tool が `readOnlyHint`・`destructiveHint`・`idempotentHint`・`openWorldHint` を
  明示する
- 分け方の規則を `main.py` の定数の隣に置き、新しい tool を足すときにも同じ規則で決め
  られるようにする。本書は tool ごとの根拠を持つ
- 宣言の付け忘れと、宣言と振る舞いの食い違いを自動テストで検出する
- `place_blueprint` の説明文の誤りを直す（TASK0016 で見つけた）
- スキル `rimworld-play` の `references/tools.md`「命令の癖」から `StockpileLarge` の
  注意を消す（fork ローカルの変更として分ける）

## 非目標

- tool の名前・引数・出力の変更と、`place_blueprint` 以外の説明の変更
- 書き込みの tool に確認の手順を足すこと。annotations はクライアントへのヒントで、何も
  強制しない
- Mod（C#）とブリッジの変更
- `title` の annotation と、resource・prompt の変更
- upstream の `upstream/main` でそのまま当たる形に整えること（裁定記録）

## 問題

- **tool は 87 個ある。** 起票時の 85 個に、TASK0006 の `get_colony_overview` と
  TASK0008 の `get_events` が加わった。`mcp_server/main.py` を構文木で読むと、55 個が
  `GET`・31 個が `POST /command/*` だけを送り、状況把握の複合 tool 1 個が複数の `GET` を
  束ねる。annotations を持つのは後の 2 個（`readOnlyHint=True`）だけである
- **ブリッジの `GET` はゲームを変えない。** `RequestRouter.HandleGet` の行き先は
  `GameStateReader` の読み出し・`/ping`・`/events` だけである。`/events` は Mod 自身の
  台帳に番号を振るが、ゲームの状態には触れない
- **宣言しないと、読み出しも書き込みに見える。** `mcp` 1.27.1 の `ToolAnnotations` の
  既定は `readOnlyHint` false・`destructiveHint` true・`idempotentHint` false・
  `openWorldHint` true である。仕様どおりのクライアントには、宣言の無い 85 個が「環境を
  破壊的に変えうる」と見えている
- **`destructiveHint` の false は「追加の更新だけをする」を意味する。** 同じ定義による。
  取り消せるかどうかではないので、既存の値を上書きする操作（速度・スケジュール等）も
  true にあたる。仕様と違う読み方で false を付けると、クライアントには実際より安全な
  意味で届く
- **annotations はヒントである。** 同じ定義が、信頼できないサーバーの annotations で判断
  しないようクライアントに求める。本作業はクライアントが区別できるようにするまでで、注入
  された指示による書き込みを止めはしない
- **宣言は振る舞いと食い違いうる。** 表だけを直して宣言と揃えても、テストは緑のままで
  ある。振る舞い（ブリッジへ何を送るか）から独立に確かめる検査が要る
- **`place_blueprint` の説明文が実装と合わない。** `CommandExecutor.Build` は
  `BuildableByPlayer` の ThingDef だけを受ける。例に挙げた 13 個のうち
  `StockpileLarge`・`TableMealSimple`・`TurretGun` はゲームの Def に無い（`Data` の XML を
  走査）。備蓄はゾーンで、建物ではない。素材の例の `Granite` は岩の Def で、素材は
  `BlocksGranite` である。素材を省いたときの既定を「最も安い」とする記述は、既定を選ぶ
  `GenStuff.DefaultStuffFor` をデコンパイラが無く読めないので確かめられない

## 概要設計

### 宣言の置き方

- 宣言は各 tool の `@mcp.tool(annotations=...)` に置く。読み手が tool の定義の場所で
  性質を読めるようにするためで、TASK0006・TASK0008 の既存の 2 個と同じ形である
- 組み合わせごとに名前の付いた定数を `main.py` に置く（読み出しの `READS_GAME`、書き込みの
  `CHANGES_GAME_ONCE`・`CHANGES_GAME_EACH_CALL`・`ADDS_TO_GAME_EACH_CALL`）。各 tool は
  定数を名指すだけにし、真偽値の並びを 87 か所に書かない。書き込みの定数は表が使う
  3 通りだけを置く
- 全ての tool が 4 つのヒントを明示する。仕様では読み出しの `destructiveHint` と
  `idempotentHint` は意味を持たないが、ヒントを 1 つずつ独立に読むクライアントには既定
  （破壊的・冪等でない）で届くので、false と true を明示する
- `openWorldHint` は全 tool で false にする。領域は 1 つのゲームのセーブで閉じている
- `RimWorldMCP.add_tool` が、4 つのヒントのどれかが未設定の登録を拒む。全 tool が
  通る関門で、`structured_output=True` を拒むのと同じ場所である。後から足した tool は、
  テストを走らせる前にサーバーの起動で落ちる。SDK の `add_tool` が関門の読む引数を
  持たなくなったときは、宣言の欠けでなく SDK の非互換として落ちる

### 分け方の規則

規則の正本は `main.py` の 4 つの定数の直上の注釈に置く。upstream へ送る側に規則を残し、
tool を足す人が起動時のエラーから辿り着く場所に置くためである。判断が割れた tool には、
デコレータの隣に理由を 1 行置く。本書は下の表で tool ごとの根拠を持つ。

### 検出の形

- **登録の関門**: ヒントを 1 つでも欠く tool は `add_tool` が拒む（宣言の置き方）
- **宣言の網羅**: 全 tool を列挙し、ヒントの欠けと `openWorldHint` を見る
- **表との一致**: tool の名前から期待する宣言への表をテストに持つ。表に無い tool も、
  tool に無い表の行も、読み出しと書き込みの両方に載る行も落とす。新しい tool を足した
  人は、表へ行を足すときに規則を当てる
- **振る舞いとの一致**: 表とは独立に、各 tool を代役のブリッジで呼び、送った要求の
  method と path を記録する。読み出しと宣言した tool が `GET` 以外を送るか、書き込みと
  宣言した tool が `POST /command/*` 以外を送れば落とす。引数は `inputSchema` の必須の型
  から作る。表と宣言を揃えて直しても、この検査は振る舞いから落ちる。ただし振る舞いから
  読めるのは `readOnlyHint` だけで、`destructiveHint` と `idempotentHint` は表だけが持つ。
  見るのは必須引数だけ・空の応答で通る 1 経路で、読んでから書く tool を足すときはこの
  検査を見直す
- 検査する tool の一覧はテストを集める時点で取る。pytest は空の一覧を 1 件のスキップへ
  潰すので、一覧がサーバーの列挙と一致することを別のテストで見る

### `place_blueprint` の説明文

- 例は、ゲームの Def にある建物だけにする（`StockpileLarge`・`TableMealSimple`・
  `TurretGun` を外し、`Table2x2c`・`Shelf`・`Turret_MiniTurret` を置く）
- 床とゾーン（備蓄はゾーン）は置けないことを書く
- 素材の例は `BlocksGranite` にする。省いたとき・defName が引けないときはゲームの既定の

  読める範囲に留め、既定の選び方（「最も安い」）は書かない
