# ブリッジの遅延と応答サイズを計測する

## 目的

ブリッジの転送方式（REST から gRPC・WebSocket へ）を替えるか、応答を絞るか、tool を
束ねるかを、推測でなく実測で決めるため。

現時点の見立ては推論にとどまる。1 回の往復は HTTP のオーバーヘッドより、ゲームスレッドの
フレーム待ちと大きな状態の直列化が支配的だと見ている。LLM のトークン消費は応答の大きさで
決まり、転送方式とは無関係だと見ている。どちらも計測していない。

## 目標

- 往復時間を 3 つの成分に分けて実測する。HTTP の受け付けまで・ゲームスレッドの
  フレーム待ち・endpoint ごとの状態の読み出しと直列化である
- keep-alive で接続を使い回した場合と、要求ごとに接続を張り直した場合の差を実測する
- 引数を取らない GET endpoint 全件と、pawn の下位パス全件の応答サイズを実測する
- 計測器を、遅延が既知のスタブサーバーに当てて較正する
- 結果と計測の条件を記録へ残す（記録層）

計測器は開発用の道具で、利用者へ届く機能を足さない。提供要求（SREQ）は採番しない。

## 非目標

- ブリッジ・Mod・MCP サーバーのコードの変更。計測は現状のコードに対して行う
- 転送方式・応答の絞り込み・tool の束ね方の決定。本作業は判断材料を出すまでとする
- POST（`/command/*`）の計測。ゲームの状態を変えるため叩かない
- MCP クライアントと MCP サーバーの間（stdio）、および LLM の推論時間の計測
- トークン数の厳密な計数。Claude のトークナイザーは手元に無いので、バイト数からの概算に
  とどめ、概算であることを記録に明記する

## 問題

- **フレーム待ちと HTTP の費用は、そのままでは分けられない。** `/ping` もキューを
  通ってゲームスレッドで処理されるため
    - 分ける手段として、ガードが拒否する要求を使う。`Origin` を付けた要求は
      `RequestGuard` がキュー投入より前に 403 で返すので、その往復は HTTP の受け付け
      だけの費用になる（TASK0003 の設計による）
    - 代償として、拒否した要求ごとにゲームのログへ警告が 1 行出る。拒否の回数は少数に
      絞る
- **計測値はゲームの状態に左右される。** マップの大きさ・入植者数・一時停止か・速度・
  fps で変わる。条件を記録へ一緒に残さないと、後で比べられない
- **共有秘密が設定されていると計測器は 403 を受ける。** 現在の環境では未設定を確認した
  （2026-09-26、`/ping` が 200）。計測器は秘密が環境変数にあればヘッダへ載せる
- 計測器を置く場所は fork ローカルの扱いになる。`CONTRIBUTING.md` が fork ローカルと
  名指すのは `CONTRIBUTING.md`・`CLAUDE.md`・`docs/` だけで、スクリプトの置き場は
  書かれていない（`tools/` を書き足すと裁定済み。裁定記録を参照）
- **ブリッジは失敗を 200 で返すことがある。** `RequestRouter` の `Ok()` は
  `GameStateReader.Error(...)` の戻り値も 200 で包む（マップが無い・pawn が見つからない
  等）。状態コードだけで成否を数えると、失敗した endpoint を成功として計測してしまう

## 到達基準

- [x] 計測器を遅延が既知のスタブサーバー（遅延 0 ms と 50 ms）に当て、中央値の誤差が
      5 ms 以内に収まる。閾値は 60 fps のフレーム間隔 16.7 ms の 3 割で、フレーム待ちを
      他の成分から見分けられる分解能として置く
- [x] 計測器が送る要求が GET と、拒否を狙った `Origin` 付きの GET だけである（POST を
      送る経路がコードに無い）
- [x] 各 endpoint の結果が、HTTP の状態コード・試行回数・中央値・p95・応答バイト数を持つ。
      200 以外を返した endpoint と、200 でも本文が `error` を持つ endpoint は、成功した
      endpoint と区別して一覧に出る
- [x] 往復時間の 3 成分（拒否要求・`/ping`・各 endpoint）が同じ実行の中で測られている
- [x] keep-alive あり・なしの差が、同じ endpoint・同じ回数で測られている
- [x] 記録が計測の条件（ゲームの状態・計測器の版・実行日時）と、トークンが概算で
      あることを明記している。fps はブリッジから取れないので、利用者の目視で得られた
      ときだけ書き、得られなければその旨を書く
- [x] 記録が、目的に挙げた 3 つの判断（転送方式・応答の絞り込み・tool の束ね方）それぞれに
      対して、実測から言えることと言えないことを分けて述べている
- [x] 第三者視点レビュー（CP6）の裁定を受けた（不要を提案し、不要と裁定された）

CP6 を不要と提案した根拠: 製品コードを変えない。計測器は 200 行前後の読み取り専用の
スクリプトで、正しさは較正（到達基準の 1 行目）で確かめる。

## 概要設計

### 計測器

`tools/measure_bridge.py` に置く。Python で書き、`mcp_server` の依存（`httpx`）を
流用して `uv run --project mcp_server` で起動する。新しい依存は足さない。

- 対象の一覧は `RequestRouter.cs` から写さず、計測器の中に明示的に持つ。ルートを
  ソースから抽出すると、抽出の誤りが計測の母数を黙って減らすため。代わりに、ソースの
  GET ルートの集合と計測器の一覧を照合し、食い違えば差分を挙げて止まる
- pawn の下位パスは `/pawns` の先頭の入植者の ID で叩く。入植者がいなければ該当する行を
  「未計測」として出し、0 件と区別する
- 各 endpoint を、捨てる 1 回に続けて既定で 20 回叩く（捨てる 1 回で接続の確立と
  初回の費用を除く）
- 出力は JSON（生の値）と Markdown の表（記録へ貼る用）の 2 つ

### 3 成分の分け方

| 計測 | 通る経路 | 表すもの |
|---|---|---|
| `Origin` 付きの `/ping` | 受け付け → ガードで 403 | HTTP の受け付けの費用 |
| `/ping` | 受け付け → キュー → 次のフレーム → 応答 | 上 + フレーム待ち |
| 各 endpoint | 上 + 状態の読み出しと直列化 | 上 + endpoint 固有の費用 |

差分を取れば各成分が出る。ただし成分の独立性は仮定である。記録ではその旨を明記する。

### 較正

同じスクリプトの中に、標準ライブラリの `http.server` で遅延を注入するスタブを持つ。
計測器を `--calibrate` で起動すると、スタブを立てて遅延 0 ms と 50 ms を測り、期待値との
差を出す。終了コードで合否を返す。

```sh
uv run --project mcp_server python tools/measure_bridge.py --calibrate
```

#### 実機

- **ブリッジの計測**
    - 目的: 往復時間の 3 成分と応答サイズを、ゲームの状態とともに得る

    - 復元手順: なし（GET だけを送る）。拒否要求 6 回分の警告がゲームのログに残る

## 作業記録

- TASK0004 は並行中の別作業（nullable 警告）が使っていたので、TASK0005 を採った
- **ブリッジは失敗を 200 で返すことがある**と、計測器を書く段で分かった。到達基準の
  「失敗の区別」に、200 でも本文が `error` を持つ場合を加えた（基準を強める向きの変更）
- 計測器を書いたあと、計画時の想定どおり利用者がゲームを用意する前に、起動中だった
  セーブ（入植直後・一時停止）で測った。速度 3 は利用者に切り替えてもらって測った
- 一時停止時に 2 回測り、系列ごとの散らばり（大半が中央値 0.5 ms 以内）を先に見てから、
  速度 3 との差を読んだ
- 計測の途中で `/world/sites` の HTTP 500 を見つけた。製品コードの変更は非目標なので
  直さず、残課題へ置いた
- **計測器は 376 行になり、CP6 を不要と提案した根拠の「200 行前後」を越えた。** 増分は
  モジュールの説明・コメントと、較正のスタブ・一覧とソースの照合である。不要の裁定は
  前提を失ったので、測った値を添えてユーザーへ差し戻した
- 計測の後、表の出力で `|` を置き換える修正を入れた。失敗の本文に `|` が含まれると表の
  行が割れるため。計測値には影響しないので測り直していない
- 中盤以降のセーブの 1 回目は、MCP Mod が有効な Mod の一覧から外れていて接続を拒否された。
  計測器はこれを「ガードが拒否しなかった」と誤って述べたので、応答が 1 件も無い場合を
  「ブリッジが応答しない」として分けた。利用者が Mod を有効にして再起動した後に測った
- **中盤以降のセーブでは、すべての往復が約 170 ms になった。** `/ping` も同じだったので、
  待ちはキューからゲームスレッドまでにあると見た。そこで、同時に送った要求が 1 回分の
  待ちで返るかを使い捨てのスクリプトで確かめた（10 本を順に送ると 1,690 ms、同時なら
  182 ms）。計画に無い計測だが、目的の「tool の束ね方」の判断材料で、GET だけを送る
- この時点で、残課題に置いていた「中盤以降のセーブで追加計測するか」は、計測を済ませた
  ので閉じた
- `frozen` を立てた後に spec-derive を回した。本作業の目標 4 件が「SREQ 未採番の新規
  候補」に出るが、いずれも開発用の計測で、利用者の知覚する外部仕様を足さないので採番
  しない（目標の節の宣言どおり）。記録を生む 1 件は随伴層として別枠に出た。TASK0001〜0004
  の候補も同じ形で残っており、要求一覧は無い（TASK0003 の裁定「新設しない」）
