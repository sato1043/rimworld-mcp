# tool の出力に含まれる不可視文字の扱いを決める

## 目的

ゲームのラベルや本文に仕込まれた不可視の文字で、LLM が人間の見ていない指示や偽の構造を
読まないようにする。

## 目標（起票時の案）

- tool の出力で、どの文字をエスケープするか（または除くか）の方針を決める。対象の候補は
  DEL と C1 制御、双方向制御、ゼロ幅文字、行と段落の区切り、タグ文字、異体字セレクター
- 方針が LLM の読み方を変えるかを、同じ出力を読ませて比べる実験で確かめる
- 決めた処理を、全 tool の直列化が集まる 1 か所（TASK0009 のラッパー）に置く

## 非目標

- ゲームの表示や Mod（C#）の出力の変更
- 可視の文字で書かれた注入への対処（TASK0012 の範囲と合わせて計画時に決める）

## 問題

- **`ensure_ascii=False` は、不可視の文字もそのまま通す。** `json.dumps` がエスケープする
  のは U+0000〜U+001F と `"`・`\` だけで、DEL・C1 制御・双方向制御・ゼロ幅文字・
  U+2028/U+2029・タグ文字は素で届く（TASK0009 の CP6 で `encoder.py` を読んで確かめた）。
  露出は TASK0009 の前からある
- **タグ文字やゼロ幅文字で書いた命令は、人間の画面に見えず LLM にだけ読める。** Mod の
  作者はラベル・手紙・クエストの本文へ仕込み、Workshop で多数の利用者へ配れる（未実測の
  推論）
- **1 行の出力では、偽の区切りと本物の区切りの見た目が近くなる。** 字下げがあった頃は
  本物のキーが改行と字下げで始まり、文字列の中に仕込んだ偽のキーと様式が違った。1 行では
  違いが逆斜線だけになる。U+2028 等をラベルに入れると、出力に現れる「改行」は必ず仕込んだ
  側のものになる（未実測の推論。LLM の読み方は測っていない）
- **閉じていない双方向制御の効果が、出力の末尾まで及ぶ。** 改行が無いので、U+202E の
  効果は 1 行に閉じない。tool の結果を人間が画面で確かめる運用で、数値や ID の並びを
  偽って見せられる（未実測の推論）
- エスケープすると、表示用の文字（異体字セレクター等）を正当に使うラベルの見え方も
  変わる。何を残すかは実験を見て決める
