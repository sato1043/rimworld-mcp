# ブリッジが要求ごとにスレッドをふさぐ作りを直す

## 目的

同時に送った要求が、ゲームの重さに関わらず 1 回分の待ちで返るようにする。止まった
ゲームに要求が積まれても、ブリッジと MCP サーバーが正しい理由で応答できるようにする。

## 目標（起票時の案）

- 同時に送った要求が、ThreadPool の空きに縛られずに同じフレームで処理される
- ゲームが止まっているときに、要求がブリッジの 15 秒の打ち切り（503）で理由とともに返る
- 変更の前後を TASK0005 の計測器で比べ、記録へ残す（記録層）

## 非目標

- 通信の方式を変えること（WebSocket・gRPC 等。TASK0005 で HTTP の費用は往復の 0.5% と
  測った）
- MCP サーバー（Python）の変更。必要なら計画時に範囲へ入れる

## 問題

- **ブリッジは要求ごとに ThreadPool のスレッドを 1 本ふさいで待つ。**
  `MCPHttpServer.Serve` はキューへ積んだ要求の完了を最大 15 秒待つ。ゲームスレッドは
  `MCPGameComponent.GameComponentUpdate` で 1 フレームに 1 回キューを処理する
- **軽いセーブでは、同時に送っても速くならない。** TASK0005 のセーブ A で `/ping` を
  同時に N 本送ると、全体の時間は N にほぼ比例した（N=8 で 127.7 ms、1 本あたり
  16.0 ms）。
  TASK0006 の複合 tool の 8 本も、順に送るのと差が無かった。空いたスレッドが少なく、
  要求が 1 フレームに 1 本ずつしか進まないためと見ている（確度 C。スレッド数は測って
  いない）。性能効率性の観点は、要求ごとに直列の費用があるという別の読みも挙げた
- **ゲームが止まると、同時に送った要求がスレッドを使い切りうる。** TASK0006 の複合
  tool は 1 回の呼び出しで 8 本を送る。一部の要求は、ブリッジの 503 より先に MCP
  サーバーの 20 秒の打ち切りに当たりうる（未実測の推論。TASK0006 の CP6 の信頼性の指摘）
- Unity の Mono の ThreadPool の最小スレッド数と、その変え方は確かめていない
