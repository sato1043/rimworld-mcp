# tool の出力から字下げを除いた前後の大きさ

- 計測日: 2026-09-26
- 対象: MCP サーバー（`mcp_server/main.py`）の tool が MCP クライアントへ返すテキスト。
  変更前は `develop`（`a580c47`）、変更後は `task/TASK0009-compact-output-impl` の
  `2a1c292`
- 計測器: `tools/measure_tool_output.py`（`7605dcc`）
- 作業書: [TASK0009](../tasks/TASK0009_compact-tool-output.md)

確度の凡例:

- **A**: 本セッションで計測を実行し、出力を直接観測した
- **C**: 推論。観測から導いたが、直接の裏付けを持たない

## 計り方

変更前と変更後の `main.py` を同じプロセスへ別々のモジュールとして読み込み、どちらも
メモリ上で起動して MCP クライアントとして tool を呼んだ。呼んだのは、`get_*` の 51 件の
うち必須の引数を持たない 36 件である（どれも GET だけを送る）。

- 変更前の実行は実行中のゲームのブリッジへつなぎ、ブリッジの応答をすべて呼ばれた順に
  記録した。変更後の実行には、記録した応答を同じ順で返した。前後は同じ本文に対する
  出力である
- 数えたのは、tool が返したテキストブロックの文字数と UTF-8 のバイト数の和と、ブロックの
  数である。ブロックの境界に MCP クライアントが足す費用は数えていない
- 前後の出力を JSON として読んだ値を比べた。変更前の `list` は要素ごとのブロックなので、
  各ブロックを 1 要素として読んだ
- あわせて、前後のサーバーが示す tool の定義（名前・説明・入力と出力のスキーマ・
  annotations）を比べた

## 計測器の較正（確度 A）

- 大きさを手で求めたスタブの本文に対し、3 つの tool の前後の大きさがすべて一致した
  （`get_weather` 21 → 16 文字、`get_messages` 0 → 2 文字、`get_pawns` 32 → 25 文字）
- 一覧を要素ごとに読む処理を外すと、較正は `get_pawns` で失敗した
- 説明文を 1 か所だけ変えたサーバーの写しを渡すと、定義の比較はその tool
  （`get_weather`）を名指した
- **最初の実機の計測で、計測器の欠陥が見つかった。** 応答を URL ごとに最後の 1 件しか
  持っていなかったので、同じパスを 2 つの tool が読むと、先の tool に後の本文を返して
  いた。`get_alerts` と `get_colony_overview` が前後で違う値として出た。どちらも、後で
  呼ぶ tool と同じパス（`/alerts`・`/state` 等）を読む。応答を順に持つよう直すと、
  違いは 0 件になった（変わっていたフィールドは特定していない）。読むたびに本文が変わる
  スタブで較正を足し、直す前の形に戻すとその較正が失敗することを確かめた。下の値は
  直した後の計測である

## 解釈（確度 C）

- `list` の縮みが `dict` より小さいのは、変更前の要素ごとのブロックが各要素を字下げ 0 段
  から書いていたためと読む。一覧全体を 1 つの JSON にして字下げした場合と比べて、要素の
  中の字下げが 1 段浅い。TASK0006 の見積もりはこの深い側で測っていた
- 縮む割合は、字下げと空白に対する文字列の値の比で決まる。日本語の長い文字列を多く持つ
  tool（`get_quests`・`get_incidents`）ほど縮みが小さい

## 測っていないもの

- 必須の引数を持つ `get_*` の 15 件と、ゲームを変える tool。これらの出力は同じ包みを
  通るので形は同じになるが、実データでは確かめていない
- ブロックの境界に MCP クライアントが足す費用。変更前の 610 ブロックが 36 ブロックに
  なったので、数えれば変更後の側がさらに小さくなる向きである
- トークン数。大きさは文字数とバイト数で比べた

## 訂正と追記（2026-09-27）

TASK0009 の CP6 の指摘を受けて、上の本文の誤りを訂正し、測っていない範囲を足す。本文は
計測した時点の記述として残す。

- **数の訂正（確度 A）。** `get_*` は 51 件でなく 52 件、必須の引数を持つ `get_*` は 15 件
  でなく 16 件である（`get_pawn_*` の 14 件と `get_cell_info`・`get_cells_info`）。呼んだ
  36 件は正しい。変更後の `main.py` の `@mcp.tool` を数えた
- **分類の訂正（確度 A）。** 「結果」の「`dict` を返す 16 件は…大きい 2 つは
  `get_animals` が -38.4%」は、表で合併型として分けた `get_animals` を `dict` の群の
  中で挙げていた。`dict` の 16 件の文字数の縮み 15.9〜43.1% は `get_animals` を含まない
  （`get_quests` から `get_drug_policies`）。TASK0006 の記録の見積もり（36〜40%）と
  比べた 2 つは、`dict` の `get_buildings`（-40.4%）と合併型の `get_animals`（-38.4%）
  である
- **測っていないものの追記。**
    - `get_` で始まらない読み出しの tool（`ping`・`list_areas`・`list_zones`）は呼んで
      いない。計測器は `get_*` だけを呼ぶ。実データで前後を比べたのは 86 件中 36 件で、
      残る 50 件は同じラッパーを通ることからの推論である
    - 大きさはトークンの代理指標である。トークン数は数えていない。数えるには出力を外部の
      API へ送る必要があり、送らないと裁定された（2026-09-27）
    - 削減率は、各 tool を既定の引数で 1 回ずつ呼んだ出力の合計に対する値である。実際の
      会話で呼ばれる tool の比や引数による重みは入っていない
    - ブリッジの共有秘密を設定した状態では計測していない。各 `main.py` が環境変数から
      秘密を読んで要求に付け、計測器は要求を保持しない、とコードから読む（確度 C）
- **計測器の版。** 上の値は `7605dcc` の計測器で測った。その後、CP6 の指摘で計測器を
  直した（各側を自分の tool 関数が返した値の型で読む・応答を tool ごとに持つ・値を型まで
  比べる等）。直した計測器で同じ比較を回し直してはいない。今回の前後の組では、変更前の
  一覧をどう読むかの結果は直す前と同じになる（直す前は変更後の形から一覧と判断していた。
  今回の変更後は一覧を配列で返すので、判断は一致する。確度 C）
- **実装の版。** 変更後は反映の前の `2a1c292` で測った。反映で出力が変わるのは `str` を
  返す tool と、JSON にできない値を返したときの失敗の形で、測った 36 件は該当しない
  （確度 C）
