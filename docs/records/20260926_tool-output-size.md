## 計り方

MCP サーバーをメモリ上で起動し（`mcp.shared.memory` の
`create_connected_server_and_client_session`）、実行中のゲームのブリッジへつないで tool を
呼んだ。LLM が受け取るのと同じテキストの文字数と、UTF-8 のバイト数を数えた。同じ
スクリプトで `main.py` の読み込み元だけを替え、変更の前後を測った。スクリプトは
スクラッチパッドに置き、追跡していない。

数えたのはテキストブロックの中身の和である。`list` を返す tool は要素ごとに別の
ブロックになるが、ブロックの境界に MCP クライアントが足す費用は数えていない（2026-09-26
追記。TASK0006 の CP6 の指摘）。

## 計測の途中で分かったこと

- **FastMCP の出力の形（確度 A。`mcp` 1.27.1 の `func_metadata.py` の
  `_convert_to_content` を読んだ）**
    - tool が `dict` を返すと、2 桁字下げの JSON で 1 つのテキストブロックにする。
      `list` を返すと、要素ごとに別のブロックにする。`str` はそのまま渡す
    - 戻り値の型注釈が `dict | list` のような合併型だと、出力スキーマが付き、同じ結果を
      structured content としてもう一度送る。`get_animals` がこれに当たり、約 12,800
      文字を重ねて送っていたので、テキストだけを送る設定にした
- **字下げの割合（確度 A）**: 変更後の 3 つの出力を、字下げと区切りの空白を除いた JSON
  にすると 36〜40% 縮む（`get_animals` 18,488 → 11,383 文字、`get_buildings`
  15,462 → 9,217、`get_animal_training` 20,717 → 13,248）。字下げは全ての tool に
  付いている
    - 2026-09-26 追記（TASK0006 の CP6 の指摘）: この 3 組は、整えた値を字下げありと
      なしで直列化し直して比べた値である。`get_animal_training` は `list` を返すので、
      実際の出力は要素ごとのブロック（17,693 文字）で、一覧全体を字下げした 20,717 文字
      とは別の量になる。実際の出力に対する割合は測っていない（出力の文字列を保存して
      おらず、測り直しには実機が要る）。`dict` を返す 2 つは実際の出力とほぼ同じ量である
- **軽いセーブでは同時に送っても速くならない（確度 A）**: TASK0005 のセーブ A で、
  `/ping` を同時に N 本送った時間は次のとおりだった。複合 tool の 8 本も、順に送ると
  56.7 ms、同時に送ると 62.3 ms で差が無かった

  | N | 全体の中央値 | 1 本あたり |
  |---|---|---|
  | 1 | 7.1 ms | 7.1 ms |
  | 2 | 17.5 ms | 8.7 ms |
  | 4 | 36.0 ms | 9.0 ms |
  | 8 | 127.7 ms | 16.0 ms |
  | 16 | 243.4 ms | 15.2 ms |
  | 32 | 373.4 ms | 11.7 ms |

- **その理由の仮説（確度 C）**: ブリッジは要求ごとに ThreadPool のスレッドを 1 本
  ふさいで、ゲームスレッドの応答を待つ（`MCPHttpServer.Serve`）。空いたスレッドが
  少なければ、要求は 1 フレームに 1 本ずつしか進まない。フレームが長い重いセーブでは、
  待つ間にスレッドが増えて並ぶ、と読む。ThreadPool のスレッド数は測っていない
